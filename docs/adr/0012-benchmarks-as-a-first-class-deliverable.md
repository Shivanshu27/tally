# ADR-0012 — Benchmarks as a First-Class Deliverable

**Status:** Accepted  
**Date:** 2026-09-28  
**Deciders:** Shivanshu Singla  

## Context

In infrastructure and distributed systems projects, architectural claims ("high throughput", "low latency", "fault tolerant", "exact reconciliation") without reproducible numbers are merely marketing diagrams. Reviewers assessing systems engineering capability look for concrete evidence:
- What throughput was sustained, on what hardware, under what CPU/RAM limits?
- What is the measured p99 latency of the hot path under load?
- How much does the fast enforcement path actually drift from the exact billing store?
- How many seconds does the aggregator take to catch up after an abrupt worker crash?
- What is the measured divergence difference when running reconciliation with vs without the completion gate?

## Decision

We treat `bench/` as a core product deliverable alongside application code:
1. We ship an asynchronous load generator capable of sustaining 10,000+ events/sec on a local developer laptop.
2. We define automated benchmark scenarios covering:
   - Sustained batch ingest throughput and latency (p50, p99, p999).
   - Hot-path quota check latency (`GET /v1/quota/check`).
   - Partition skew under hot-tenant 10x traffic.
   - Crash recovery catch-up time after simulated kill.
   - Enforcement drift percentage against the exact store.
   - Reconciliation divergence: gated (0.00%) vs. ungated (noisy false positives).
3. All published benchmark results in `README.md` must be generated by running the harness on local hardware, recording hardware specs, container configurations, and the exact CLI execution commands.

## Consequences

### Positive
- Validates that theoretical design claims hold true under actual stress.
- Provides immediate regression detection when algorithmic or database optimizations degrade performance.
- Establishes undeniable technical credibility for the portfolio codebase.

### Negative
- Running comprehensive benchmark scenarios takes developer time and CPU cycles.
- Benchmark results will vary across different machines and operating systems; documentation must clearly state test conditions.
- Requires building and maintaining load generation harnesses, statistical aggregators, and markdown report formatters.

## Alternatives considered

- **Theoretical algorithmic analysis without execution**: Easy, but fails to expose real-world bottlenecks like connection pooling, serialization overhead, and GC pauses.
- **Third-party tool benchmarks (e.g. k6/wrk) only**: Useful for HTTP endpoints, but cannot measure internal streaming properties like partition lag, watermark progression, and completion-gated reconciliation diffs.
